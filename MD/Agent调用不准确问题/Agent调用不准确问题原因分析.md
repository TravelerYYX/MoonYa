# MoonYa Agent 调用不准确问题原因分析

> 本文记录修复前的真实故障链路、数据库授权事实和测试盲区。配套修复见《Agent调用不准确解决方案.md》。

## 一、核对结论

原分析只覆盖了“岗位描述不清、模型可能选错”这一层，方向部分正确，但不足以解释已经出现的严重错调用。真正的问题由四条链路共同造成：

1. Work 路由让模型直接填写 `agent_key`，岗位边界只有简短描述，服务端没有独立、唯一、可校验的能力归属。
2. Work 根协调者和员工的工具授权过宽，多个岗位可用通用 Shell/Python 绕过职责边界。
3. 当前用户消息可能先由前端写进数据库，后端读取历史时再次读到它，然后又向模型追加一次；历史还取的是最早 20 条。
4. Work 最终回复只显示为过程节点，没有作为正式 AI 消息保存。刷新后 user/assistant 对不完整，旧执行任务更容易被模型误认为当前任务。
5. 代码已更新但目标数据库未执行种子迁移时，`multi_agent_v1` 配置不存在；旧代码把这种情况当成“团队未启用”并静默退回单 Agent 工具路径。

这不是一个单纯的“提示词准确率”问题，而是路由协议、权限边界、消息持久化和失败状态语义同时存在缺口。

## 二、修复前的真实调用链

### 1. Work 根协调链路

修复前的主要路径为：

1. `api.php` 构造系统消息、数据库历史和当前用户消息。
2. `TeamWorkProtocol::prepareInitialRequest()` 向 MoonYa 暴露委派工具。
3. MoonYa 在 `delegate_to_agents.tasks[*]` 中直接填写 `agent_key`、`instruction` 和依赖。
4. `TeamCoordinator::validateTasks()` 主要检查 Agent 是否在委派白名单、任务 ID 和依赖是否有效。
5. 选中的员工获得数据库 `agent_tool_grants` 中的全部工具并进入执行循环。
6. 员工返回结果后 MoonYa 进行最终总结。

这里没有独立的“能力实体”。岗位选择、Agent 选择和工具可用性被混在同一次模型输出中；服务端只能判断“这个 Agent 能不能被委派”，无法判断“这个能力是否唯一属于它、完成能力所需工具是否齐全”。

### 2. `tool_choice` 的真实边界

强制 `tool_choice` 只能约束模型响应采用工具调用形式，不能阻止模型在内部推理，也不能证明它选对岗位。

DeepSeek thinking 模式还有兼容限制：启用 thinking 时需要移除不受支持的 `tool_choice`。因此系统不能把正确性建立在“所有模型都能被强制调用某个函数”这一假设上。即使没有强制 `tool_choice`，协议仍必须依靠提示词、工具 Schema 和服务端状态机正确区分“直接回复”与“委派执行”。

## 三、修复前的实际工具权限问题

“所有 Agent 都有 `create_file`、`edit_file`、`read_file`”不是事实。数据库种子中只有部分岗位拥有文件工具；真正的问题是通用执行器被过度分配，以及岗位之间存在越权能力。

修复前重点问题如下：

| Agent | 问题性授权 |
|---|---|
| MoonYa | Work 根协调阶段仍可能接触普通 Agent 模式的业务工具；缺少强制服务端隔离 |
| App | 除应用生命周期工具外还拥有 Shell、Python、命令状态和停止命令 |
| Computer | 拥有 Python；Work 中可直接 `open_app`，破坏 App → Computer 分工 |
| Browser | 拥有 Shell、Python、命令状态和停止命令 |
| Search | 拥有 Shell、Python、命令状态和停止命令 |
| File | 文件能力最完整，但 Office 依赖未形成受管运行时契约 |
| Code | 需要项目文件、执行器和 LSP，但通用文件删除、移动、打开等边界不清 |

两个工具允许合理共用，不能用于反推岗位：

- `web_fetch` 同时服务 Search 和 Browser。联网调研属于 Search；读取或交互指定网页属于 Browser。
- `download_file` 同时服务 App 和 File。应用安装包属于 App；普通文档、图片和资源属于 File。

因此，按“哪个 Agent 拥有这个工具”做 `LIMIT 1` 查询无法正确路由。一个工具可以有多个合法拥有者，决定岗位的是能力语义和边界，不是工具所有权的第一条记录。

## 四、历史串话的完整根因

这是原分析遗漏的核心故障。

### 1. 当前消息重复进入上下文

前端 `sendMessage()` 先把当前用户消息加入 DOM，然后触发 `saveCurrentChat()`。旧逻辑没有真正等待正在进行的保存队列完成，保存请求与 AI 请求可能并发。

如果当前消息已经由 `conversation_api.php` 保存，`api.php` 随后查询历史时会把它读出来；构造模型上下文时又会无条件追加当前 `$message`。于是同一条用户请求在上下文中出现两次。

### 2. 历史查询取错方向

旧 SQL 使用：

```sql
ORDER BY created_at ASC
LIMIT 20
```

它得到的是最早 20 条，不是最近 20 条。长会话中，新近完成状态和最近 user/assistant 配对被丢弃，早期执行任务反而长期留在模型窗口中。

只按秒级 `created_at` 排序也不稳定。连续快速消息可能具有相同时间，需要使用稳定、单调的消息主键排序。

### 3. Work 最终回复没有成为正式消息

Work 的 `.team-agent-message` 负责展示过程和最终团队节点，但 `saveCurrentChat()` 只收集普通 `.message.user/.message.ai`。因此 `assistant.completed` 可能在页面上可见，数据库却没有对应 AI 消息。

刷新后会话只剩用户执行请求，没有它已经完成的 AI 回复。下一轮短句或闲聊到来时，模型看到的是一个未闭合的旧任务，很容易继续执行旧任务。

### 4. 按内容全历史去重会吞消息

前端曾用“角色 + 去标签后的文字”扫描全部已保存消息，历史加载还按 AI 正文全局去重。这会把用户有意连续发送的两条相同文字错误合并。

正确的幂等边界必须是消息 ID，而不是内容。没有 ID 的旧记录只能对“最后一条、同角色、同内容”的紧邻消息做一次兼容兜底。

## 五、路由与失败恢复问题

### 1. 普通对话没有独立协议出口

闲聊、需要补充信息和不支持请求不应调用员工。只有委派工具时，模型要么错误委派，要么直接输出普通文字并触发协议错误。

### 2. 跨岗位任务可被整体塞给一个 Agent

“搜索资料并生成 docx”“打开应用后操作界面”包含两个有先后关系的能力。没有能力级 Schema 和依赖校验时，模型可能因为某个 Agent 工具较多就把整件事交给它。

### 3. 校验失败可能被当成空成功

预执行校验失败若只返回空结果，后续逻辑可能把“0 个失败”解释为成功并进入总结。校验错误与员工执行失败也共用委派次数，导致一次可纠正的规划错误消耗执行重试额度。

### 4. 没有员工证据也可能生成完成总结

如果综合阶段只看工具调用是否结束，而不检查是否存在真实员工结果，就可能把纯文本、空数组或全部失败包装成“已完成”。

### 5. Work 运行时不可用时曾错误降级

2026-07-31 的“清空回收站”现场日志给出了完整证据：请求携带 `agent_mode=agent`，但数据库 `agent_runtime_config` 中没有 `multi_agent_v1` 和 `function_calling_compatibility`。后端没有创建 `team_run`，没有发送 `run.started`，而是进入旧 `agentTools` 分支，把 `shell_executor` 等业务工具直接交给 MoonYa。界面因此同时出现“MoonYa 直接执行 PowerShell”和右侧“团队尚未开始工作”。

这类故障不能只靠补跑迁移处理。只要 Work 已被用户选择，团队表未安装、配置缺失、配置关闭或初始化异常都必须失败关闭：返回结构化 `team_runtime_*` 错误，禁止退回单 Agent；若异常发生在 `team_run` 创建之后，还必须发送失败事件并将运行收口为 `failed`，不能遗留 `running` 记录。

## 六、Office 产物能力缺口

File Agent 虽有 Shell 和 Python，但受管 Python 环境没有固定的 Office 依赖清单，日志中出现过 `ModuleNotFoundError: pptx`。

此外，旧契约没有强制要求：

- 保存到用户指定路径；
- 重新打开产物；
- 检查 docx 关键段落、xlsx 工作表、pptx 幻灯片或 PDF 页数；
- 将最终文件作为 artifact 返回。

因此“调用 Python 成功”不能等同于“Office 产物已完成并验证”。

## 七、风险元数据问题

多个会改变外部状态的工具曾被标为只读或低风险，例如网页爬取、窗口聚焦、鼠标移动、打开文件、生成图像/视频等。

`browser_automation_control` 还是一个多 action 工具。截图与读取、导航与填写、上传与提交敏感数据的风险不同，不能只使用工具级固定风险。

## 八、原有测试盲区

原 smoke test 的假服务固定挑选 Computer Agent，测试通过只能证明“预设的 Computer 可以执行”，不能证明数据库能力解析正确。

缺失的覆盖包括：

- App、Computer、Browser、File、Search、Code 全岗位能力归属；
- Search → File、App → Computer 依赖链；
- 闲聊直接回复；
- 多个 Agent 共用同一工具；
- Browser/Search 调用 Shell/Python 的服务端拒绝；
- 超过 20 条消息、快速连续发送、相同文字、刷新恢复；
- 当前闲聊不能重放旧的“清空回收站”；
- DeepSeek thinking 模式没有强制 `tool_choice` 的路径；
- 校验拒绝、规划纠正、部分成功、审批拒绝、取消和最终状态；
- Office 文件的真实生成与重新读取；
- 迁移重复执行及管理员自定义/MCP 授权保护。

## 九、最终判断

严重错调用的根因不是“模型不够聪明”，而是系统没有给模型和服务端一个可验证的能力路由协议，同时消息历史又把已完成旧任务伪装成当前未完成任务。

必须同时修复：

- 能力 → 唯一 Agent → 必需工具的数据库关系；
- Work 根协调者与员工的最小权限；
- 当前消息和最终回复的 ID 幂等持久化；
- 最新历史的稳定排序；
- 拒绝、纠正、执行和综合的状态证据；
- Office 运行时和风险审批。

只改提示词或增加关键词规则，无法形成可靠闭环。
